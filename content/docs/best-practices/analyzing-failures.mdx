The [test report](/docs/results/run-report) tells you **what** failed. This
page is the loop for **why** — and where the fix belongs.

## Find the cause

1. Start at the [summary report](/docs/results/run-report#summary-report):
   which cases didn't pass, and with which status?
   - **`FAILED`**: the application misbehaved — or the test told the agent
     the wrong thing. Continue with step 2.
   - **`BROKEN`**: infrastructure, not the application — device lost,
     session expired, model unreachable. Two ways to resolve:
     - **Fix the issue itself** — the network, the hardware, the session
       ([Troubleshooting](/docs/troubleshooting)).
     - **Or let the agent resolve it**: give it a
       [rule](/docs/writing-tests/setup-teardown-rules#rules) plus a
       [tool](/docs/extending/custom-tools) — e.g. "if the scanner stops
       responding, use the `restart_scanner` tool and repeat the step."
   - **`WARN`**: passed with a caveat — read the report's **Issues**
     section; often the early sign of a real problem.
   - **`SKIPPED`**: an entry criterion wasn't met, or an
     [optional step](/docs/writing-tests/step-constructs#optional) didn't
     apply. Check the **Preconditions** section.
2. Open the failing case's [test report](/docs/results/run-report) and read
   the failed step:
   - **Agent Interpretation** — did the agent understand the step the way
     you meant it? If not, the defect is in the test.
   - **Expected vs. Actual**, plus the step screenshot — if the expectation
     is right and the application really did something else, you've found a
     product defect.
3. Still unclear? Switch from the test report to the
   [conversation log](/docs/results#conversation-log) — it shows what the
   agent actually did, in detail: every decision, tool call, and screenshot
   on the way to the failure.
4. Before closing: scan **Issues** — also on tests that passed. The agent
   notes anomalies there (slow responses, odd dialogs) that are often the
   early warning for the next run's failure.

## Fix it

Match what you saw to the pattern — each has one remedy.

- **The agent misclicks.** The
  [locator](/docs/writing-tests/step-constructs#locators) is ambiguous on
  this screen.
  - **Fix:** make the element description more specific — text + color +
    position. Still not enough? Enable the **Screen zoom**
    [tool](/docs/extending/tools).
- **The agent takes a lot of steps.** It is unsure how your application
  behaves.
  - **Fix:** add
    [UI information](/docs/writing-tests/agents-and-prompts#ui-information)
    — "the pop-up stays open when you click it" — and make vague goals more
    precise.
- **FAILED, but the behavior is actually correct.** The agent judged against
  the wrong picture: your expected result is under-specified.
  - **Fix:** state more precisely what the expected result looks like.
- **PASSED, but it actually failed.** The success criterion is too loose to
  catch the defect.
  - **Fix:** add an explicit
    [verification step](/docs/writing-tests/step-constructs#verifications)
    after the action.
- **Odd path, but the right result.** That's
  [non-determinism by design](/docs/concepts/how-a-run-executes#why-execution-differs).
  - **Fix:** nothing — judge the result, not the path.
- **The agent operates the UI wrong** — shortcuts, keyboard instead of the
  numpad. It doesn't know your house style.
  - **Fix:** teach it in
    [ui_information](/docs/writing-tests/agents-and-prompts#ui-information)
    or [rules](/docs/writing-tests/setup-teardown-rules#rules).
- **Random real-world disruptions** — the app hangs, the printer is empty.
  The environment, not the test.
  - **Fix:** give the agent the manual tester's recoveries in
    [rules](/docs/writing-tests/step-constructs#beyond-steps).

### Not the agent's behavior?

- **Wrong starting state** → the suite's
  [setup](/docs/writing-tests/setup-teardown-rules).
- **Credentials failed** → [secrets](/docs/extending/secrets) — values are
  per machine; a colleague's fresh clone starts without them.
- **The device didn't come up** → [Devices](/docs/devices) and
  [Troubleshooting](/docs/troubleshooting/connection-sessions).
- **The application genuinely misbehaved** → your bug tracker. The test
  report with its screenshots **is** the incident evidence — attach it.
