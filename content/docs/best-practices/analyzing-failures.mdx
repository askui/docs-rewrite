The [test report](/docs/results/run-report) tells you **what** failed. This
page is the loop for deciding **why** — and where the fix belongs: in the
product, in the test, or in the environment.

## Triage by status

Start at the [summary report](/docs/results/run-report#summary-report) and
take each non-passing case by its status:

| Status | First suspicion | Go to |
| --- | --- | --- |
| `FAILED` | The application misbehaved — or the test told the agent the wrong thing | The failed step, below |
| `BROKEN` | Infrastructure, not the application: device lost, session expired, model unreachable | [Troubleshooting](/docs/troubleshooting) |
| `WARN` | Passed with a caveat — often the early sign of a real problem | The report's **Issues** section |
| `SKIPPED` | An entry criterion wasn't met, or an [optional step](/docs/writing-tests/step-constructs#optional) didn't apply | The **Preconditions** section |

## Read the failed step

1. Read the **Agent Interpretation** — did the agent understand the step the
   way you meant it? If not, the defect is in the test: sharpen the wording
   ([Writing good tests](/docs/best-practices/writing-good-tests),
   [Step constructs](/docs/writing-tests/step-constructs)).
2. Compare **Expected** vs. **Actual** and look at the step screenshot. If
   the expectation is right and the application really did something else,
   you've found a product defect — the report with its screenshot **is** the
   incident evidence; attach it to the ticket.
3. Still unclear? Open the
   [conversation log](/docs/results#conversation-log) — the complete record
   of every decision and screenshot on the way to the failure.

## Failure keeps coming back?

**The agent took an odd path but the result was right** — that's
[by design](/docs/concepts/how-a-run-executes#why-execution-differs); judge
the result, not the path. \
**The agent keeps misreading the same element** — sharpen the
[locator](/docs/writing-tests/step-constructs#locators): more distinguishing
features, spatial anchors. \
**The agent operates the UI wrong** (shortcuts, keyboard instead of numpad)
— teach the house style in
[ui_information](/docs/writing-tests/agents-and-prompts#ui-information) or
[rules](/docs/writing-tests/setup-teardown-rules#rules). \
**Random real-world disruptions** (hanging app, empty printer) — give the
agent the manual tester's recoveries in
[rules](/docs/writing-tests/step-constructs#beyond-steps).

## Where the fix belongs

| Symptom | Fix it in |
| --- | --- |
| Step wording was misunderstood | The test case — [phrasing](/docs/best-practices/writing-good-tests) |
| Expectation was too vague to judge | The step's expected result |
| Wrong starting state | The suite's [setup](/docs/writing-tests/setup-teardown-rules) |
| Credentials failed | [Secrets](/docs/extending/secrets) — values are per machine |
| Device didn't come up | [Devices](/docs/devices) / [Troubleshooting](/docs/troubleshooting/connection-sessions) |
| Application genuinely misbehaved | Your bug tracker — with the test report attached |
