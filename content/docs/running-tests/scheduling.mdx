---
title: Scheduling
description: Run a test or plan automatically, daily at a time, every N minutes or when watched files change, while AskUI Desktop is open.
---

A schedule runs a test or [test plan](/docs/writing-tests/plans)
without you pressing Run. A test runs on the device profile you pick in
the dialog; a plan runs on the device recorded in the plan. A scheduled run
whose device is busy [queues silently](/docs/running-tests#if-it-cant-start-right-away)
and starts when the device is free.

<Callout type="warn" title="A closed app means missed runs">
Schedules fire only while AskUI Desktop is running, it is not a background
service. Close the app, or let the machine sleep or shut down, and the
scheduled run does not happen at its time. If the app is back later the same
day, the missed daily run starts then; a day that passed entirely while the
app was closed is skipped, no firing, no report. For runs that must never be
missed, the nightly regression, use the [CLI](/docs/running-tests/cli) on a
build server with your CI scheduler.
</Callout>

A daily schedule you save, edit or switch back on after its time has passed
today waits for the next selected day. Saving "weekdays at 05:00" at 16:00 on
a Tuesday starts nothing until Wednesday 05:00.

## Manage all schedules in one place

The **Runs** page's sidebar has two views, **Runs** and **Schedules**. The
Schedules view lists every schedule of the project permanently, each with
an on/off toggle, a pencil to edit its cadence, and delete. The **+**
button creates a new one: pick any plan or test of the project in **What
to run**. The Dashboard shows the next few upcoming schedules at a glance.

## Create a schedule

1. Open the test on the **Tests** page (or the plan on **Test Plans**).
2. Click the alarm-clock button, the **Scheduled runs** dialog opens,
   prefilled with this file.
3. Pick the **Device profile** (for a plan this step disappears, the
   plan's own devices are used).
4. Pick the **Cadence**: **Daily at a time** (with weekdays) or
   **Every N minutes**.
5. Click **Add schedule**.

The dialog lists every schedule in the project with its last outcome, the
run's results, or why it was skipped (e.g. the device could not connect).
Schedules live in the project's `schedules.json`. A due schedule never
double-fires, even when a run outlasts its interval.

## Pause or delete a schedule

The dialog lists every schedule in the project:

1. Untick the **on** checkbox to pause a schedule, it stays configured but
   stops firing (the row dims).
2. Click the trash button (**Delete schedule**) to remove it.

There is no edit: to change the cadence or device, delete the schedule and
add it again.

## Run When a File or Folder Changes

A **File trigger** starts a test plan when files it watches change on disk,
for example when an export or a build drops new files into a folder. Like a
schedule, it fires only while AskUI Desktop is open.

1. On **Test Plans**, click the plan's trigger button (the lightning bolt).
2. Click **Add trigger** and set **Trigger type** to **Files**.
3. Click **Add folder…** or **Add file…** and pick it in your system's dialog.
   A folder counts as changed when any file inside it, at any depth, is added,
   changed or deleted. Add as many entries as you need, one per line.
4. Pick **Fire when**: **Any watched file or folder changes**, or **All
   watched files and folders have changed**. With All, the plan starts once
   every entry that is switched on has changed since the last run, in any
   order.
5. Click **Add trigger**. The plan's row shows **File Trigger**.

Files that already exist when you add an entry never start a run. Only
changes made after that count. The trigger checks for changes every 30
seconds.

### Manage the Watched Files and Folders

Each line shows the file or folder's name. Hover it to see the full path.

- **Pencil**: picks another file or folder in its place. On Windows, the
  dialog opens with the current entry selected.
- **Switch**: pauses the entry without removing it. A change made while an
  entry is paused never starts a run, even after you switch it back on.
- **Trash**: removes the entry.

When you edit a File trigger that already exists, each of these changes is
saved at once, so **Done** keeps exactly what the list shows.

A run started by a File trigger shows a folder icon in the **Runs** list. Its
tooltip names the files or folders that changed. Watched paths are absolute,
so a teammate who opens the project on another computer sees the entries,
but they start nothing until those paths exist there.
