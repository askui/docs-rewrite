Every test in a run ends with exactly one **status** and a short reason. The
status tells you what the run found out about your system. The reason says
what was expected and what was observed.

Read a status as an answer to one question: **what do we now know?**

## The seven statuses

| Status | What it means | Who sets it | Conclusive | Who acts |
| --- | --- | --- | --- | --- |
| `PASSED` | The expected outcome was observed. | The agent | Yes | — |
| `WARNING` | The expected outcome was observed, but something noteworthy happened on the way, for example a slow response or a small visual deviation. Counts as passed. | The agent | Yes | — |
| `FAILED` | **A proven defect.** The agent's action reached the right target, and the system answered wrongly or not at all. | The agent | Yes | The product team |
| `SKIPPED` | The feature or capability the test needs does not exist on this system. | The agent, or a setup that records `SKIPPED` | Yes | — |
| `UNCLEAR` | The agent could not tell whether the system behaved as expected. The reason names what was missing and where the agent looked. | The agent, or AskUI when the agent ended without a status | No | The owner of the test or the device profile |
| `BROKEN` | The test system failed: a crash, a tool or infrastructure error, a device that stopped answering. Nothing is known about the system under test. | The agent, or AskUI when the test crashed | No | The owner of the bench or environment |
| `BLOCKED` | The run never finished this test: a setup it depends on did not pass, an earlier test broke the run, or the run was stopped. | AskUI only | No | Follow its reason |

### PASSED

Every step ran, and the expected outcome was observed. A `PASSED` test is
evidence that the feature works on this system.

### WARNING

The test passed, and the agent noticed something you should know: the screen
took several seconds to respond, a label was cut off, an extra dialog had to
be closed. `WARNING` counts as passed everywhere. Read the reason to decide
whether it needs a ticket.

### FAILED

The system under test behaved wrongly, and the agent has the evidence. The
agent records `FAILED` only when two things are true:

- its action verifiably reached the intended target, which a screenshot
  shows, and
- the system answered wrongly or not at all, or an element the test or the
  device profile says must be there is verifiably absent.

A `FAILED` test is a defect you can file. If the agent cannot prove the
defect, it does not record `FAILED`.

### SKIPPED

What the test needs does not exist on this system, so there is nothing to
test. The [device profile](/docs/devices) or the
device's capabilities say so, for example "no navigation app on this head
unit" or "no antenna on this bench". `SKIPPED` is a known fact about the
system, not a failure.

When a [setup](/docs/writing-tests/setup-teardown-rules#how-a-setup-or-teardown-ends)
records `SKIPPED`, every test of its folder is `SKIPPED` with the setup's
reason. When the setup gave no reason, the note reads "Not run: a setup it
depends on found what it prepares not available." Those tests are conclusive
too.

### UNCLEAR

The agent could not tell whether the system behaved as expected. Typical
causes:

- a page, path, or element was not found, and nothing shows that it should
  be where the agent looked;
- the agent's action may not have registered;
- the screen stayed in a state the agent could not interpret.

`UNCLEAR` is the last resort. The agent records it only after it tried
the paths the device profile and the test name suggest, made a second
attempt, and took a fresh screenshot after waiting. The reason always names
what was missing and where the agent looked. That reason is your to-do: most
`UNCLEAR` tests turn conclusive once the device profile names the
missing path.

A test that ends normally without recording any status is `UNCLEAR`
too, with the reason "The test ended without recording a result."

**Who acts:** the owner of the test or the device profile. Add the missing
path to the device profile, or sharpen the test.

### BROKEN

The test system failed, not the system under test: the device stopped
answering, a tool or the controller returned an infrastructure error, a
custom tool threw an exception, the test crashed. A `BROKEN` test tells you
nothing about your product. Fix the environment and run it again.

**Who acts:** the owner of the bench or environment. Fix the device, the
tool, or the connection.

If the agent recorded a status before the crash, that status stands, and the
conversation shows a notice about the crash.

### BLOCKED

The run never finished this test. AskUI sets it, never the agent. The reason
says why:

| Reason | When |
| --- | --- |
| Not run: a setup it depends on failed. | A setup of its folder ended `FAILED`, `UNCLEAR`, or `BROKEN`, or it crashed. |
| Not run: `<test>` broke the run before this test. | An earlier test crashed, and the run ended there. |
| Not run: the operator stopped the run before this test. | You stopped the run before this test started. |
| The run was stopped during this test. | You stopped the run while this test ran. |
| Not run: the run failed before this test. | The runner failed before this test started. |
| The run ended during this test. | The runner failed while this test ran. |

A `BLOCKED` test is not a skipped one: nothing was learned about it.

**Who acts:** follow its reason. Fix the setup or the test that broke the
run, or run the tests again.

<Callout type="info" title="Tests marked in the test file">
A test whose file marks it `DISCARDED` or `DEPRECATED` keeps that status. It
counts as nothing: it is neither conclusive nor not conclusive.
</Callout>

## Conclusive and not conclusive

Pass and fail alone don't tell you how well the automation works. A system
with many defects gives many failed tests, even with a perfect automation.
So AskUI groups the statuses into two classes:

- **Conclusive:** `PASSED`, `WARNING`, `FAILED`, `SKIPPED`. The run learned
  something about the system: it works, it is broken, or the feature is not
  there.
- **Not conclusive:** `UNCLEAR`, `BROKEN`, `BLOCKED`. The run learned
  nothing about the system for this test. Something in the test setup, the
  device profile, or the environment needs attention.

Aim for as few not-conclusive tests as possible. They point at work on your
side, not at defects in the product.

Environment problems are meant to be visible and owned. AskUI does not hide a
broken bench behind a failed or skipped test, so the owner of the bench sees
the problem and can fix it.

## Pass rate and conclusive share

The [summary report](/docs/results/run-report#summary-report), the
[Dashboard](/docs/results/dashboard), the
[Management Report](/docs/results/management-report), and the CLI show two
figures:

- **Pass rate** = passed ÷ (passed + failed). `WARNING` counts as passed.
  Skipped and not-conclusive tests are left out, so the pass rate only
  speaks about tests that produced a pass-or-fail answer.
- **Conclusive share** = conclusive ÷ (conclusive + not conclusive). It tells
  you how much of the run produced knowledge.

Example: a run of 30 tests on a head unit without navigation. 6 passed,
1 failed, 21 skipped (the navigation tests among them), 1 unclear,
1 blocked.

- Pass rate: 6 ÷ (6 + 1) = **86 %**.
- Conclusive share: (6 + 1 + 21) ÷ 30 = **93 %**.

## Exit codes in CI

The [CLI](/docs/running-tests/cli#exit-codes) turns the statuses into its
exit code, so a pipeline can stop on defects only:

| Exit code | When | What to do |
| --- | --- | --- |
| `0` | Nothing failed, and every test is conclusive. A run where every test was `SKIPPED` is `0`: "not available" is a result. | Nothing. |
| `1` | At least one test is `FAILED`. This wins over everything else. | File the defect. |
| `5` | No test failed, but at least one is `UNCLEAR`, `BROKEN`, or `BLOCKED`, a setup did not pass, or the runner failed. | Fix the test environment, the device profile, or the test. |

A run you cancel with Ctrl+C ends with `130`, whatever the statuses. The
other exit codes are in the [CLI reference](/docs/running-tests/cli#exit-codes).

In [JUnit XML](/docs/results/export#junit-xml), `FAILED` is a `failure`.
`UNCLEAR`, `BROKEN`, and `BLOCKED` are an `error`. `SKIPPED`,
`DISCARDED`, and `DEPRECATED` are `skipped`.

## How the agent picks a status

1. The expected outcome was observed → `PASSED`, or `WARNING` with a note.
2. A tool or the infrastructure failed → `BROKEN`.
3. The device profile or the capabilities say the feature is not available
   → `SKIPPED`.
4. There is evidence that the system behaved wrongly → `FAILED`.
5. Otherwise, after the known paths were tried twice → `UNCLEAR`, with
   what was missing and where it looked.

The agent reads these rules from AskUI's
[status definitions](/docs/extending/reporting#status-definitions).

## Runs from earlier versions

Runs recorded before AskUI knew `UNCLEAR` and `BLOCKED` keep their
statuses. In those runs, `SKIPPED` can also mean "never started", and a
setup that failed counts as broken. Their pass rate is now computed as
passed ÷ (passed + failed), so a run with broken tests shows a higher pass
rate than before.
