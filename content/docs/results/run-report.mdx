A run records three things: the **result** of each test, an **execution
report** per test, and the run-level **summary report**. Where they live and
how to open them: [Runs](/docs/results).

## Test result

The agent ends each test by recording its result: one status and a short
reason, for example `FAILED`, "Expected the dashboard, saw an error
banner.". The recorded result decides whether the test passed. The summary
report, the Dashboard, the [Management Report](/docs/results/management-report),
and the [CLI](/docs/running-tests/cli)'s exit code all count it.

The agent picks the status by AskUI's
[status definitions](/docs/extending/reporting#status-definitions). The
status is one of:

- `PASSED`: the actual result matches the expected one.
- `FAILED`: the test executed, but the result didn't match.
- `WARNING`: the expected outcome was observed, but something noteworthy
  went wrong on the way (slow response, minor visual deviation). Step lines
  in a report write it as `WARN`.
- `SKIPPED`: intentionally not executed (e.g. a precondition was not met).
- `BROKEN`: could not execute: a crash or an infrastructure failure.

The reason names what was expected and what was observed. A test that ends
without a recorded result is `BROKEN`, with the reason "No result recorded".
A test that stops on an error is `BROKEN`, with the error as the reason. If
the agent records more than once, the last result counts. The result is saved next to the test as `<test_name>_result.json`.

## Execution report

The execution report is the written record of one test: what the agent did,
what it expected, and what it observed, with screenshots. The agent that ran
the test does not write it. A separate agent writes it after the test ends:
it reads the test's conversation and screenshots and follows your project's
[report format](/docs/extending/reporting#report-format). The next test
starts at once, so a report never slows a run down.

Whether a test gets a report, and which model writes it, you set under
[Extending → Reporting](/docs/extending/reporting). A test without a report
can get one later from the **Runs** page:
[Write a report later](/docs/results#write-a-report-later).

Section by section:

- **Test metadata**: who, when, and how it went.
  - **Test Case ID**: ties the report to the
    [test case](/docs/writing-tests), its title ID or file name.
  - **Date**: when the test executed.
  - **Status**: the [result the test recorded](#test-result). The report
    states it as given and cannot change it.
  - **Cost of this test**: right behind the status. The test's execution
    cost comes first, and the total including this report follows in
    parentheses, for example `$0.3315 ($0.4137 with reporting)`. When only
    the report's cost is known, it reads `$0.0822 for the report`. Without
    a known price, the cost is left out. The cost also adds to the run's
    total, which the summary report in the app shows as
    **Cost of this run:**.
- **Summary**: the outcome in two sentences, read this first.
- **Preconditions**: whether the assumed starting state was actually met,
  a test that began from the wrong state fails here, not misleadingly in a
  step.
- **Test Steps**: one entry per step.
  - **Agent Interpretation**: how the agent understood your instruction,
    check this when a step surprises you.
  - **Expected** / **Actual**: the step's contract and what was actually
    observed.
  - **Status**: the step's own status: `PASSED`, `FAILED`, `SKIPPED`,
    `WARN`, or `BROKEN`.
  - **Screenshot**: the step's evidence. The writer picks it from the
    screenshots the agent took during the test, so the numbers in the file
    names (`screenshot_<n>.png`) need not run in order.
- **Postconditions**: whether the overall pass criterion held at the end.
- **Issues**: anything worth a look that isn't a failure, the incident
  notes. In the example above: the 15-second sign-in.
- **Conclusion**: the closing assessment of the whole case.

The report's shape is defined by your project's
[report format](/docs/extending/reporting#report-format). To share a report
with someone without the app, export it as PDF or JSON:
[Export](/docs/results/export). What to do with a failing report, triage,
root cause, where the fix belongs:
[Analyzing failures](/docs/best-practices/analyzing-failures).

### Files of a test

Each test has its own folder in the run folder:

| File | Holds |
| --- | --- |
| `<test_name>_result.json` | The recorded result: status, reason, start and end time. |
| `<test_name>_report.md` | The execution report. |
| `screenshot_<n>.png` | The screenshots the report embeds. |
| `<test_name>_report.json` | The report's state (`ready` or `failed`, with the error), the model, the tokens, and the cost. |

---

## Summary report

`summary_report.md` in the run folder summarizes the whole run: a totals head
(test-case count, per-status counts, run duration), one Markdown table across
all tests with status and execution time per test, and detail sections that
quote the recorded reason of each warned, failed, or broken test.

```markdown
# Summary Report

**Date:** 2026-08-06

**Total:** 3 Test Cases
- **✅ Passed:** 2
- **❌ Failed:** 1
- **⏱️ Duration:** 00:04:03

| Test Case ID | Test Case Name | Status | Duration |
| --- | --- | --- | --- |
| login_test | login_test | ✅ Passed | 00:01:12 |
| settings_test | settings_test | ✅ Passed | 00:00:48 |
| checkout_test | checkout_test | ❌ Failed | 00:02:03 |

# ❌ Fails

## checkout_test
The pay button never appeared after entering the voucher code.
```

The summary comes from the recorded results, not from the execution
reports, so it is complete even for tests without a report. A test that ran
but recorded no result reads "No result recorded". Tests that a
[test plan](/docs/writing-tests/plans) selected but the run never reached are
listed as `💥 Broken` with a duration of `—`, so nothing goes missing
silently. The Dashboard and Runs pages in AskUI Desktop derive their pass/fail
counters from this table. The summary report pane exports the run as PDF or
JSON: [Export](/docs/results/export).

<Callout title="Counting rules">
`WARNING` counts as passed (tracked separately in the warning total).
`SKIPPED` tests never executed and are excluded from the total. `BROKEN`
tests without an execution time in the summary (tests that never started)
are also excluded from the total, they show in the table but don't affect
the pass rate.
</Callout>

In CI, upload the whole workspace folder as a build artifact so the reports
and screenshots stay attached to the run even when tests fail:

```yaml title=".github/workflows/ui-tests.yml"
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: askui-run
    path: agent_workspace/
```
